## [0.5.0-dev.3] - 2026-10-05

### Added

- Sony hFT-Transformer piano transcription backend (`type: hft_transformer`, ISMIR 2023, two-level frequency-then-time Transformer predicting a piano-roll representation, trained on MAESTRO V3, upstream <https://github.com/sony/hFT-Transformer> pinned at commit `71a2ee06e9ced1ea24673c95ee0acded2fc98d04` with the network and note decoding vendored under `src/sonitra/transcribe/_hft/` and its MIT `LICENSE` alongside): config keys `device` (unified `cpu` / `cuda` / `cuda:N` / `GPU:N`, default `cpu`), `checkpoint: maestro`, `weights_path` (an already converted file; the upstream `.pkl` pickle is refused by name), `output` (`second`, the time-axis head set the paper reports and the default; `first` selects the frequency-axis set), `n_stride` (0–64 frames of 16 ms, 0 = no overlapping windows), `onset_threshold` / `offset_threshold` / `mpe_threshold` (each default 0.5) and `batch_size` (default 1), with per-file `metadata` recording `output_head`, `n_stride`, `batch_size`, `thresholds`, `resampler: pedalboard`, `sample_rate: 16000`, `upstream_commit`, `checkpoint`, `weights_sha256`, `note_events_total`, `notes_kept`, `filtered_dropped` and `offset_past_end` beside the usual device and numeric-mode keys. The released checkpoint is a pickled `nn.Module` with `cuda:0`-tagged tensors and cannot be loaded at runtime, so `scripts/setup_hft_transformer.py` downloads the pinned release asset, verifies its size and sha256 against the registry, converts it once into a `model.pt` that `torch.load(weights_only=True)` accepts, and writes a `manifest.json` recording the provenance next to it — run `python scripts/setup_hft_transformer.py` once; both containers run it on start, and its exit codes are `0` installed or already installed, `1` failure, `2` usage error, `3` torch absent (checked before any download, so an `INSTALL_TRANSKUN=0` image skips quietly). Weights resolve under `$SONITRA_MODELS_DIR` when set and non-empty, else `~/.cache/sonitra/models`, never repo-relative, at `<models_dir>/hft_transformer/maestro/model.pt`; in containers the host `models/` is bind-mounted at `/models` with `SONITRA_MODELS_DIR=/models`, and `SONITRA_SETUP_HFT=0` skips the start-up step for air-gapped hosts. No new extra and no dependency change: torch already comes from the `transkun` extra. Licence position: the vendored code is MIT (Copyright 2023 Sony Group Corporation) but the release asset states no licence and the weights derive from MAESTRO under CC BY-NC-SA 4.0, so Sonitra neither redistributes nor commits them. Shared torch process state moved to `src/sonitra/transcribe/torch_support.py` (`apply_torch_numeric_settings`, `validate_torch_device`, `numeric_settings_from_env`, `missing_dependency_error`) with one process-wide applied-settings cache, because torch's numeric flags and device state are process-global and two torch backends can share a worker; the cuBLAS workspace default is set only for `numeric_mode: strict` on a CUDA device. Measured on the maintainer's machine (RTX 4090 Laptop GPU, CPU inference via PyTorch 2.12.1) against three MAESTRO v3 test-split pieces rendered to audio from MIDI with a GM SoundFont — rendered-audio numbers, not real-recording numbers, so the real MAESTRO recording comparison is still outstanding — hFT-Transformer reaches note onset F1 (duration-weighted) 0.9746 (per file 0.9730–0.9801) against TransKun's 0.9965, note onset+offset F1 0.906 against 0.944, and note onset+offset+velocity F1 (duration-weighted) 0.673 against 0.796. Three caveats travel with those numbers: velocity is the weak axis, so onset detection is near parity while velocity is not; `note.onset_offset_f1` is a lower bound for a reason that is not the model, because its training references are pedal-extended (note-off forced at the CC64 pedal release) while `src/sonitra/midi_reader.py` has no `control_change` branch and so reads references 22.2 % shorter than the model's own training references (+993.5 s measured against +180.4 s), which makes onset F1 the convention-neutral number for the comparison; and CPU real-time factor 0.43–0.44 (~2.3× faster than realtime) with the pure-Python note decoder at 1.9–2.1 % of CPU time, so `batch_size` stays at 1 because batching buys almost nothing on CPU while multiplying peak resident memory about 4.2×. On CPU at `batch_size=1` the vendored path is bit-for-bit identical to the upstream reference implementation across 43 windows and both window modes, CPU against CUDA diverges by up to 3.3e-04 on the velocity logits (70–75 of roughly 75 note-list entries changing in the last bits), and Sonitra's `pedalboard` resampler moves log-mel values by as much as 5.4 against upstream's torchaudio path while leaving onset F1 0.0019–0.0028 higher, so published numbers must name the device and `transcription.numeric_mode` and cannot be compared against upstream's published figures directly. Documented in `docs/model-cards.md`, `docs/configuration.md`, `docs/reproducibility.md`, `docs/docker.md`, `docs/devcontainer.md`, `docs/adding-a-transcriber.md`, `README.md`, `AGENT.md`, `ARCHITECTURE.md` and `ROADMAP.md`; `docs/model-cards.md`'s generated baselines block is untouched, since this backend has no qualifying benchmark run yet and the existing omitted-models note covers it.

## [0.5.0-dev.2] - 2026-10-05

### Added

- `TuningOffset` effect for a global detune: `src/sonitra/effects/builtin_effects.py:101` adds `TuningOffsetConfig` (`cents` required, validated finite and within ±1200; the other eight fields are `pedalboard.time_stretch`'s own defaults), and `src/sonitra/effects/chain_builder.py:44` adds `TuningOffsetStage`, which applies the shift through `pedalboard.time_stretch` (Rubber Band's offline pitch/time stretcher) instead of the `PitchShift` plugin, because that plugin does not apply cent-level shifts reliably and a small shift comes out as no shift at all. A `cents: 0` slot returns the signal untouched without reaching the stretcher, so an enabled zero-cent slot stays a passthrough; a length drift from the stretcher is trimmed or zero-padded back to the input length, and a changed channel count raises rather than writing a transposed buffer. A global offset cannot live inside a `pedalboard.Pedalboard` because the stretcher is a plain function, so `build_effects_chain` (`chain_builder.py:149`) returns a `CompositeEffectsChain` that keeps each run of native plugins in one `Pedalboard` segment around the offset stages, collapsing to a single segment (and unchanged output) when no offset is enabled, and warns at build time when an enabled offset reaches ±50 cents, where notes may score as the neighbouring pitch. `src/sonitra/effects/base.py` adds `__len__` to the `EffectsChain` protocol, which `src/sonitra/pipeline.py:106` uses to skip an empty chain. The six configs in `config/benchmark/paper_experiments/` gained the two leading slots and nine tuning conditions each: `inst=piano_tune=-32c`, `-20c`, `-8c`, `8c`, `12c`, `20c`, `-40c`, `40c` and `rt40c` in the five piano configs, the same nine names without the `inst=piano_` prefix in `guitar_only.yaml`, each enabling slot 0 and switching every other slot off, with `rt40c` enabling slot 0 at +40 cents and slot 1 at -40 cents as a round-trip control. New smoke configs `config/benchmark/smoke/tuning_piano_test.yaml` (MAESTRO test split, `io.sample` of two files) and `config/benchmark/smoke/tuning_guitar_test.yaml` (GuitarSet) reuse the same chain layout and run three of those conditions plus the baseline; both take MIDI input, so they synthesise the dataset's reference MIDI and need no recordings in the corpus, and `benchmark.save_audio` writes the renders so the offset can be heard. `scripts/estimate_tuning.py` measures each recording's own tuning offset from A440 (`librosa.estimate_tuning` / `librosa.pitch_tuning` at `--sample-rate` 22050 and `--resolution` 0.01) and writes the per-reference CSV named by `--output`, a `<stem>.recordings.csv` per-recording table beside it, and a `<output>.provenance.json` sidecar, refusing any output that is, or lies inside, one of its input directories. Covered by `tests/test_tuning_offset.py`, `tests/test_estimate_tuning.py`, `tests/test_chain_builder.py`, `tests/test_config.py` and `tests/test_fingerprint_compat.py`; documented in `config/source.yaml:179-192`, `docs/configuration.md`, `docs/cli.md`, `docs/statistical-analysis.md` and `config/benchmark/README.md`

### Changed

- The six configs in `config/benchmark/paper_experiments/` gained two leading `TuningOffset` slots, so every pre-existing effect slot moved by +2 (`pedalboard.effects.0` Reverb is now `.2`, `.1` Chorus is now `.3` and `.2` Distortion is now `.4` in `piano_only.yaml`, and the guitar chain shifts the same way) and every condition's dotted-path overrides were rewritten to match. `tests/test_fingerprint_compat.py` re-captured `GOLDEN_PIANO_ONLY_PRESET`, from `3840432d6e2f670ab9372c89d570359d9b2c9401eec5454442ac8f19f082f069` to `8ff383745f82e281ea5ad321476bbfa56527cefa145f961bea3964968be8d26d`, because `compute_fingerprint` (`src/sonitra/benchmark/results.py`) hashes the whole config; `GOLDEN_VALID_CONFIG` is unchanged. Every existing work directory for those six configs therefore stops resuming with a fingerprint mismatch (`src/sonitra/benchmark/runner.py:397`) and the runs have to be redone together. The re-run costs about ten extra passes over each corpus per audio preset (the eight single offsets plus the two round-trip legs) at a measured 4.86 % of real time for stereo audio (2.92 s per audio minute, 20.4 s for a 7-minute file), so a 20-hour corpus adds roughly 10 extra CPU-hours per audio preset. Those configs render one file at a time, because `synth_backend: fluidsynth` never takes the threaded per-file path (`src/sonitra/pipeline.py:242`), so the parallelism available there is across conditions through `benchmark.max_workers` (a `ProcessPoolExecutor` in `src/sonitra/benchmark/runner.py:487`). Exported regression tables label the two new slots `override.pedalboard.effects.0_TuningOffset.cents` and `override.pedalboard.effects.1_TuningOffset.cents`, so column names from older paper runs no longer line up. `librosa>=0.11.0,<0.12` is now declared directly in `pyproject.toml` instead of arriving transitively through basic-pitch.

- Numeric reproducibility settings `transcription.numeric_mode` (`Literal["off", "warn", "strict"]`, default `"off"`) and `transcription.gpu_memory_growth` (bool, default `false`) added to `src/sonitra/config.py:TranscriptionSection` and surfaced in `config/source.yaml`.
